How to fix inconsistent financial metrics in NetSuite

If your metrics change depending on which report you pull or which tool you ask, the fix isn't in NetSuite — it's in the layer underneath it.

Start with the data layer, not the dashboard

It is tempting to fix inconsistent metrics by rebuilding the dashboard. But if the dashboard reads the same ambiguous data, the problem comes back. Start one level down: extract NetSuite data reliably on a schedule (Fivetran, SuiteQL or a similar connector), land it unchanged, and do all the transformation in one version-controlled place, such as dbt.

Define each metric once, use everywhere

Write each metric — gross margin, EBITDA, DSO, recognised revenue — as code, with its accounts, filters and currency rules explicit. Store the definitions alongside a plain-English description finance signs off. Reports, spreadsheets and AI tools then read the finished metric rather than recomputing it. If the definition changes, it changes everywhere at once, with a record of who changed it and why.

Automate reconciliation instead of doing it in Excel

Automated tests replace the month-end spreadsheet checks. Typical examples: the trial balance nets to zero; the modelled TB ties to NetSuite's TB for every period and subsidiary; every GL account is mapped to a reporting line; no posting lands in a closed period after close. Tests run on every refresh, so a break is spotted the day it happens rather than on day five of close.

What ongoing data engineering looks like

NetSuite keeps changing: new accounts, subsidiaries, custom fields and workflows. Ongoing work is mostly keeping the model in step — mapping new accounts, adding schedules finance asks for, and investigating any test that fails. Done well, it is a few hours a month, and most of it happens before anyone notices a number was about to be wrong.
